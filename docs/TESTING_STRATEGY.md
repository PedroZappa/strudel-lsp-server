Testing is mandatory. The framework and supporting tooling were evaluated and selected based on project requirements, and the decision is recorded here.

## Framework evaluation

| Option                    | Strengths                                                                                       | Costs                                                                                                       | Assessment                                     |
| ------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Node built-in `node:test` | Zero dedicated test dependency; ESM support; suitable for module, protocol and subprocess tests | TypeScript tests need a compile step or an execution helper; less built-in ergonomics than a full framework | Selected                                       |
| Vitest                    | Mature TypeScript/ESM support, watch mode, mocking and coverage; widely used                    | Additional dependency; Node version requirement; more tooling to maintain                                   | Useful if rich test ergonomics prove necessary |
| Mocha                     | Present in prototype devDependencies                                                            | Existing setup is broken; no tests; older toolchain assumptions                                             | Rejected                                       |

Local environment at 2026-11-25: Node v26.8.2, npm 11.19.1.

## Decision

Use Node's built-in test runner over compiled ESM JavaScript, with the TypeScript compiler producing test output. This avoids a separate test-framework dependency while still supporting module, protocol and subprocess tests.

An execution helper such as `tsx` may be evaluated for watch-mode developer ergonomics, but is not adopted. Installing any further dependency requires explicit approval.

Rationale: the built-in runner covers the required module, protocol and subprocess tests, keeps the dependency surface small, and works with the pinned TypeScript toolchain. Vitest remains a documented alternative if richer ergonomics become necessary.

## Test quality requirements

- Tests are deterministic and do not rely on network access at runtime.
- Generated fixtures record source versions and provenance.
- Live-coding fixtures include incomplete chains, partial calls, malformed mini-notation and rapid edits.
- Error paths are tested, including missing metadata and cancelled requests.
- Parser corpus tests remain separate from semantic engine tests.
- Capability advertisement is verified against implemented features.
- Performance benchmarks are maintained separately from correctness tests.
- Every bug fix adds or updates a regression test that fails before the fix.
- Tests are not changed, weakened, skipped or deleted merely to make validation pass.

- `npm run test:soak` — build, then run only `dist/test/soakLifecycle.test.js` bounded lifecycle and advisory memory-observation tests.
- `npm run smoke:clients` — build, then run local VS Code and Neovim smoke clients against the stdio server and print their behaviours.
- `npm run smoke:clients:write` — the same two-client run, refreshing `validation/client-smoke.json` only when both clients pass.
- `npm run smoke:vscode` and `npm run smoke:nvim` — run one local client when only one editor is available.
- `npm run validate:corpus` — build, then validate syntax, semantics and incremental reuse over the pinned Strudel documentation examples and compare with `validation/real-corpus.json`.
- `npm run validate:corpus:write` — deliberately regenerate the committed corpus evidence report after a reviewed change.
- `npm run generate:metadata` — regenerate the committed snapshot from pinned local inputs.
- `npm run benchmark` — build and run all benchmark workloads with p50/p95/p99 output.
- `npm run benchmark:check` — build, rerun the workloads and compare them with the committed thresholds.
- `npm run benchmark:baseline` — deliberately regenerate the committed baseline after a validated change.
- `npm run benchmark:e2e` — build, pack and install the server offline, then print p50/p95/p99 for one JSON-RPC request through the installed bin without writing a report.
- `npm run benchmark:e2e:write` — the same measurement, refreshing `benchmarks/end-to-end.json` as advisory evidence rather than a threshold baseline.
- `npm run verify:package` — build, pack with an isolated npm cache, verify tarball contents, install offline from the tarball using the surrounding cache and exercise the stdio executable.
- `npm run verify:contents` — build, pack with an isolated npm cache, assert the tarball allowlist and print the package contents without installing.
- `npm run verify:consumer` — build, pack, install into an isolated consumer directory with empty npm configuration, a fresh cache and `--legacy-peer-deps=false`, then verify the manifest, licence, parser prebuild and stdio launch in both script modes.
- `npm run verify:release` — build, verify the release version/tag/commit, compare `npm pack --dry-run` with `npm publish --dry-run` in an isolated copy, and check the manifest and tarball allowlist without publishing.
- `npm run check` — chains typecheck, lint, format verification and the full test suite.

Test discovery uses quoted glob patterns instead of bare directories. Node 24 interprets positional `node --test` arguments as glob patterns and attempts to load a directory as a module; Node 26 additionally accepts directories. `test/packageScripts.test.ts` verifies that the suite patterns use globs and together cover every compiled suite file.

The `Makefile` provides convenience targets for these commands; `make check` runs the same combined gate as `npm run check`, `make test-parser`, `make test-semantic`, `make test-metadata`, `make test-configuration`, `make test-lsp`, `make test-features`, `make test-mini`, `make test-protocol` and `make test-soak` run isolated suites, `make validate-corpus` and `make validate-corpus-write` wrap corpus validation, `make generate-metadata` regenerates the snapshot, `make benchmark`, `make benchmark-check`, `make benchmark-baseline`, `make benchmark-e2e` and `make benchmark-e2e-write` wrap the benchmark scripts, `make smoke-clients`, `make smoke-clients-write`, `make smoke-vscode` and `make smoke-nvim` wrap the local client smoke scripts, `make pack-check` wraps the hermetic package-content preview, `make verify-package` wraps the packaged installation check, `make verify-consumer` wraps the isolated consumer-install check, and `make verify-release` wraps the non-publishing release candidate check.

Dependencies are installed with `npm ci --ignore-scripts` from the committed `package-lock.json`, matching the documented local install. npm download caching is keyed to that lockfile. Actions are pinned to commit SHAs with version comments, the workflow has `contents: read` permissions, and newer runs for the same ref cancel superseded runs. The editor-client smoke harness is deliberately local-only: hosted runners do not guarantee an installed VS Code application or Neovim, and adding one would introduce an editor dependency outside the published server contract.

CI does not publish packages or change Git state. Release publication remains a separately authorised workflow; the parser redistribution licence gate was resolved by the AGPL-3.0-only decision in ADR-032 and is recorded in `docs/ROADMAP.md`. `npm run verify:package` uses the npm cache populated by the clean install in the same job; it verifies the local tarball, installed licence metadata and offline operation, not publication. Performance regression reporting is advisory as documented in `docs/PERFORMANCE.md`; the correctness gate remains blocking.

Prototype directories remain outside the lint/format/build scopes. The committed `src/languageDatabase/generated.ts` snapshot is inside those scopes and must be generator-formatted. Results must be reported honestly; failures are not suppressed to make validation pass.

### Protocol robustness review (2026-11-27)

Phase 11 added `test/protocolRobustness.test.ts`, a raw stdio harness that spawns the built server, writes LSP frames directly, parses every stdout frame, and fails on unframed bytes, invalid JSON-RPC envelopes, partial frames or unexpected stderr. Eight deterministic tests covered stdout purity after malformed JSON bodies and envelopes, unknown methods, invalid parameters, `$/cancelRequest` during a bounded workspace scan, stale edits, document closure, no-workspace and multi-root initialization, normal shutdown and abnormal exit. The ninth test—unchanged diagnostics defaults without `workspace.configuration` followed by a settings-notification change—was added with the Phase 14 configuration work (ADR-052); the final suite has nine tests.

The review confirmed that stdout contains only framed JSON-RPC messages, malformed JSON bodies are ignored, malformed envelopes receive framed `window/logMessage` notifications, unknown methods return `-32601`, handler failures do not stop the server, and LSP exit codes are correct: 0 after `shutdown` then `exit`, 1 for `exit` without `shutdown`.

Three gaps were fixed:

- `initialize` previously threw on a non-array `workspaceFolders` value and returned internal-error `-32603`; optional fields are now validated and treated as absent.
- A client that did not advertise `workspace.workspaceFolders` could receive a `workspace/workspaceFolders` request for a workspace symbol query and hang a minimal client; the request is now made only when the capability was advertised.
- A lower document version arriving after a newer version could still be scheduled because `latestVersions` was overwritten before the deferred task ran; stale versions are now rejected at the scheduling boundary, and the regression test verifies the newer content survives.

Evidence:

- `npm run check` passed with 63/63 tests at that point, including strict typecheck, lint and Prettier verification; the final Phase 14 gate is 85/85.
- `npm run test:protocol` passed the eight raw stdio tests in 510 ms on Node v26.8.2, darwin-arm64.
- `make test-protocol` passed through the Makefile wrapper.
- `npm run verify:package` passed both offline install modes, native parser prebuild load and installed stdio handshakes on darwin-arm64.
- `npm run benchmark:check` passed all 18 workloads within the committed thresholds; no layer-level latency regression was observed.
- The clean-install OS matrix and corpus validation were not rerun for this server-only change; their existing evidence remains in this document and `validation/real-corpus.json`.

The design decisions and consequences are recorded as ADR-038 in `docs/DECISIONS.md`.
